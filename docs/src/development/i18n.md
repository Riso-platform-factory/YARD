# i18n: strings in the user's language

An application made with YARD shows text from three places:
- the platform itself: the menus, the window buttons, "Close", "Dismiss", the settings editor, the command palette, the updater's toasts;
- the application;
- its extensions.

Today all of it is English, written as literals. This slice gives YARD a string catalog, picks a language from a setting or the system, and moves the platform's own text into catalogs, in English and, as the proof, Vietnamese. An application and its extensions add their own strings the same way.

## Design

Zed at rev `ddb90e5` is English only, and GPUI has no locale, formatting, or right-to-left support. The design follows:
- Flutter's ARB files and Apple's string catalogs: one file per language, keys namespaced by owner, English as the fallback;
- Project Fluent's arguments and plural selection.

The options compared:
- **Project Fluent:** good syntax, but its plural rules come from an unmaintained 2022 crate, and its identifiers forbid the `.` YARD uses for namespaces.
- **rust-i18n:** a process-wide locale, which breaks parallel tests, and per-crate tables.
- **gettext:** bundles LGPL C code.

So YARD keeps a small catalog of its own, in JSON read with `serde_json`, which it already has. Plural rules come from ICU4X `icu_plurals`, under the Unicode-3.0 licence of the ICU4X crates already in `Cargo.lock`. The locale comes from `sys-locale` and `icu_locale_core`, both already locked. The sources are in the proposal.

## Catalogs

- **One JSON object per language and owner.** Keys map to strings:

  ```json
  { "close": "Close", "update.installed": "{name} {version} is installed", "items": { "one": "{count} item", "other": "{count} items" } }
  ```

  - `{name}` is an argument.
  - An object with CLDR plural categories (`zero`, `one`, `two`, `few`, `many`, `other`) is a plural, chosen by `count` with the language's CLDR rules from `icu_plurals`. `other` is required, and a category the language does not use is ignored.
- **Every owner registers under its namespace:**
  - the platform's crates under their crate names (`yard_ui`, `yard_shell`, `yard_update`, `command_palette`, `settings_editor`);
  - the application under `app`;
  - an extension under its extension name.

  A key is `<namespace>.<key>`, split at the first dot. An owner cannot add keys to another's namespace.
- **Reserved namespaces:** `app` and every name starting with `yard_` belong to the application and the platform's crates. An extension handle registering under them is refused with `CatalogError::ReservedNamespace` and an `info!`. A platform extension such as `command_palette` registers through its own handle under its own name, which no other extension can have.
- **Registering again replaces** that namespace's catalog for that language, keys omitted included. Locale tags compare without regard to case. A malformed replacement is refused and the previous catalog stays.
- **The files are compiled in** with `include_str!`, one per language: `locales/en.json`, `locales/vi.json` beside the owner's `Cargo.toml`. The application's files are in `app/<name>/locales/`.
- **A namespace** is non-empty and has no dot; **a key** is non-empty. **A malformed catalog** (not a JSON object, a value that is neither a string nor a plural object, a plural without `other`, or a key repeated at either level) is refused at registration, with one `ERROR`. It is a bug in the build.

## Choosing the language

- **The setting:** `settings.json` section `"language"`, field `"locale"`, a BCP-47 tag such as `"vi"` or `"en-GB"`. It defaults to `null`, which means the system's language.
- **The system's language** comes from `sys-locale`. `C` and `POSIX` count as no language. Requested tags (the setting and the system's) are accepted with `_` as well as `-` (`vi_VN`), and a POSIX encoding or modifier suffix (`.UTF-8`, `@euro`) is dropped. A catalog's own tag is strict BCP-47: `en.` or `en.foo` is refused and never replaces a registered catalog.
- **Negotiation:** the requested locale, then its parents (`vi-VN` to `vi`), then English. A language with no catalog at all falls back to English, with one `info!` inside `locale-apply`, never for English itself.
- **The section is editable** (`register_editable_settings`), so the settings editor shows it. The tag is a text field in this slice.
- **Changing the setting applies at once,** without a restart:
  - every window is redrawn;
  - the menus are rebuilt;
  - views that keep a string (the settings editor's field labels, the command palette's open list) take the new language.
- **Tests run in English** unless they set the setting. They never read the host's language.

## What code writes

```rust
yard_i18n::t(cx, "yard_ui.close")                                         // "Close" / "Đóng"
yard_i18n::t_with(cx, "yard_update.installed", &[("name", name), ("version", v)])
yard_i18n::t_count(cx, "app.items", n)                                    // plural, with {count}
ext.register_strings(cx, "vi", include_str!("../locales/vi.json"));       // under the extension's name
```

- **`t` returns a `SharedString`, so every `yard_ui` component takes it unchanged.** No public parameter type changes in this slice.
- **A view calls `t` in `render`,** so a redraw shows the new language.
- **A lookup walks the language's parents** before English: `vi-VN`, then `vi`, then `en`; `zh-Hant-TW`, `zh-Hant`, `zh`, then `en`. One owner registering a regional catalog never hides another owner's `vi` strings.
- **Every entry point works before `init`:** the first registration creates the catalog in English, and `init` adds the setting and the system language. The platform's crates can register their strings while they start, in any order. A lookup before anything was registered cannot create it (GPUI creates a global only with mutable access), so it returns the key and warns.
- **A missing key:**
  - shows the English string;
  - if English lacks it too, shows the key itself;
  - logs one `log::warn!` per locale and key in the diagnostic log, and exactly one lifecycle event per lookup. `yard_log` forwards `log` records into the trace, so the first miss must not appear twice;
  - never panics.
- **The application's menus** are built from a function that now also takes `&App`, so they can call `t`. `yard_app` keeps the function and calls it again when the language changes.
  - The macOS Window menu is still found by its English name `"Window"`, which GPUI requires. Its shown title is translated.

## What moves into catalogs (English and Vietnamese)

- **`yard_ui`:**
  - "Close", "Close Tab", "Close <label>", "Dismiss";
  - "Minimize", "Maximize", "Restore";
  - "Select…", "No items".
- **`yard_shell`:** "New Item".
- **`yard_update`:** "<name> <version> is installed", "is available", "Restart".
- **`command_palette`:** its placeholder, its empty message, and its other built-in text.
- **`settings_editor`:**
  - its title;
  - "Modified", "Reset", "Use default", "Edit in settings.json";
  - its refusal messages;
  - its section and field titles that YARD writes itself. Doc comments from an extension's type stay in that extension's language.
- **The sample application's menus** (`app/yard/src/menus.rs`), and the template's (`tooling/xtask/templates/new-app/`).

The `vi` catalog covers every key of the platform's `en` catalog. A test checks that both files have the same keys. The bundled IBM Plex Sans covers Vietnamese.

## Parts and order

Production code cannot use dev code, so the work is two steps, each reviewed:

1. **The engine** (`crates/yard_i18n`, dev part `yard_i18n/catalog`, and `yard_shell`'s `Extension::register_strings` as a dev part):
   - the catalog;
   - `t`, `t_with`, `t_count`;
   - negotiation;
   - the `language` section;
   - applying a change;
   - the logging.

   It is tested, committed, and promoted on its own.
2. **The move:**
   - the production parts named above change in place to call `t` and register their catalogs, and are stamped again;
   - `yard_app/startup` registers the `language` section, resolves the locale, and rebuilds the menus on a change;
   - the test extension `examples/i18n_tour` (`I18N_TOUR=1`) registers its own `en` and `vi` strings, with a plural and an argument, and shows them beside platform text.

## Logging

- **`catalog-register{namespace, locale, keys}`:** `debug!("registered")`; `ERROR` for a malformed catalog. The key count is a field of the group when it opens, since `yard_log` keeps only the fields a group starts with.
- **`locale-apply{requested, resolved}`:** `debug!("applied")`, with the source (setting or system), around the redraw and the menu rebuild.
- **Lookups are per frame:** `trace!` only, except a missing key's `warn!`.

## Tests

Written first by a worker that does not write the code.

- **Negotiation:** `vi-VN` resolves to `vi`; `fr` and `C` resolve to `en`; the setting beats the system.
- **Lookup:** arguments; plurals in `en` (1 is `one`; 0, 2, and 5 are `other`) and in `vi` as CLDR rules them in the `icu_plurals` data YARD ships (CLDR 49: `one` for 0 and 1, `other` otherwise). The categories always come from that data, never from rules written in YARD. Also the fallback to English, then to the key.
- **Logging:**
  - a missing key's `warn!` is once per key in the diagnostic log, and on every lookup in the trace;
  - a malformed catalog is refused;
  - namespaces cannot be crossed;
  - the logging tests run 20 times.
- **Live change:** with `TestApp`, changing the `language` setting re-renders a view's text and rebuilds the menus.
- **The platform's catalogs:** `en` and `vi` have the same keys; every key used in the code exists in `en`.

## Not in this slice

- Right-to-left layout (roadmap #40).
- Number, date, and currency formatting.
- Translating doc comments into the settings schema.
- A list of languages as a choice in the settings editor.
- macOS `CFBundleLocalizations`, so system dialogs follow the app's language.
- Key names in key hints on Linux and Windows (Zed's `KeyBinding` writes "Ctrl", "Shift").
- Translating `yard_ui`'s public parameters into keys (a `Text` type).
